# Monitoring and disk investigation

The agent records health, HTTP latency, host CPU/memory/swap/load/uptime/root-disk metrics and Docker CPU/memory/network counters. Updated host collectors also read logical CPU/task counts, available/cache memory, swap capacity, non-loopback interface bytes/packets/errors/drops and Linux pressure-stall information. Missing metrics are explicitly listed. Host CPU is calculated from two `/proc/stat` samples; it is a point-in-time observation, not a long-term average. Docker CPU may exceed 100% on multicore hosts.

Host network charts derive bytes/second from recorded cumulative counters. Reboots, counter resets, changed interface identity, absent values and gaps over three minutes leave rates unknown. The totals include virtual interfaces and bridges, so they are interface traffic rather than unique internet traffic. Error/drop totals are cumulative since counter reset. Pressure uses PSI `some avg10`: the percentage of time over the last ten seconds when some tasks stalled. Kernels without readable PSI files show unavailable pressure. New fields need the updated session collector or optional VPS history agent; old agent payloads continue to work with missing extras shown as dashes.

CPU/RAM refresh every second through direct kernel-file reads; these counters require no helper process or new SSH session. Container stats and inventory/root disk refresh every 30 seconds. Public HTTP defaults to 30 seconds; DNS/TLS use five minutes. Host resource history is written every 15 seconds and workload history follows its 30-second samples. Unchanged health is saved at most once per minute; meaningful transitions are saved immediately. Inventory history is written only on a change, while current inventory and health state stay fresh. The [configurable history policy](history.md) defaults to two days of metrics, seven days of routine history, one year of operational evidence and a 256 MiB main database budget. Current records and open incidents are preserved; old history can be pruned sooner under size pressure. Every collection/import writer applies maintenance, including one-shot commands. Historical queries remain bounded to 1,000 records.

The dashboard runs its collector automatically. `hostops-agent` can keep full collection running against the same database while the dashboard uses `--no-collect`. The optional narrow VPS service instead keeps only 30 minutes of host resources; it does not record ongoing site health or workloads while the dashboard is closed. CLI status/doctor and the dashboard share a three-minute health freshness rule; `--max-age` explicitly changes the CLI limit. Stale healthy evidence becomes unknown and status/doctor exit with code 2. See [discovery](discovery.md) for shared-backend accounting and per-observation cadence.

```sh
hostops metrics --config local/hostops.json
hostops metrics client-a --config local/hostops.json
hostops history client-a --config local/hostops.json --since 24h
hostops disk --config local/hostops.json
```

`disk` scans the top-level directories of the root filesystem with a 45-second bound and runs Docker's disk accounting. Set `host.disk_roots` to narrow an investigation or include separately mounted filesystems; scans stay within each selected filesystem. Directory totals overlap their child entries and must not be added together. Permission/time/output limits are shown rather than concealed. The command never prunes, deletes or changes retention. Accounting identifies candidates for investigation; it cannot determine that a volume or backup is safe to remove.
