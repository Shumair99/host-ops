# Production readiness and improvement queue

Readiness measures recorded production evidence, not uptime, speed, security certification or the probability that a website works. Its five categories are availability (20 points), deployment safety (15), recovery (20), security (20) and observability (20). The full checklist totals 95 points. The former five-point rollback rule was removed because no observation can verify a retained rollback release; there is no hidden five-point deduction.

Passing rules earn their stated weights. Missing, stale or failing observations earn zero. Explicitly skipped checks are excluded from the applicable maximum and never count as passes. Caddy-served redirects do not require a separate app image, runtime user, memory limit, restart policy or app resource samples. Docker-specific rules are skipped for known non-container runtimes. Missing container ownership remains unknown rather than being treated as inapplicable. Missing hardening fields remain unknown until actually observed.

The dashboard shows a normalized percentage and the underlying earned/applicable points. For example, 25/50 applicable points is 50% evidence coverage for a redirect, not 25% website health. `Provisional` means at least one applicable rule is unknown. The detail separates points missing through unknown evidence from points unmet through failed checks. A fully observed assessment can still have failed rules. Historical raw scores used different applicability rules and should not be compared directly.

Fresh runtime/health means less than three minutes old. Independent watcher and resource observations must also be recent. Backup evidence must be within the configured RPO (24 hours by default); restore evidence must be health-verified within 30 days. The dashboard presents failed/unverified rules as a prioritized improvement queue within each property. A deployment notification alone does not prove a retained rollback image exists.

The points increase through verified observations: working public HTTP/proxy/runtime/TLS checks, a running image ID and source revision label, an appropriate restart policy, observed Docker hardening settings, recent backup and restore reports, retained health/resource samples, and a fresh independent watcher report. Image-ID traceability in Readiness is separate from Security's image-reference check: a running image can have a known ID while its configured `latest` tag remains mutable.

See [the operations tools guide](operations-tools.md) for impact, recovery, maintenance and security explanations.

Confirmed apex/www redirect pairs share one dashboard assessment for the serving application. Their independent HTTP/TLS checks remain in Health log. Redirect failures also appear in the combined assessment, without inventing a second application's requirements. Separate subdomain applications remain independent. This grouping requires an observed redirect to an observed counterpart; arbitrary subdomains are not merged.

Process permissions use current effective UIDs, not just Docker's configured USER. Recognized Nginx supervisor/non-root-worker arrangements retain a warning and earn no non-root points while the supervisor remains root. Their role is explained without relaxing the common least-privilege criterion. Incomplete identities remain unknown. Automated backup-job reports discovered on the VPS contribute the same validated evidence as local imports; detected files alone earn no backup or restore points.
